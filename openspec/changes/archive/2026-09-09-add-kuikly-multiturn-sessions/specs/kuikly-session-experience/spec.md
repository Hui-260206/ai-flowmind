## ADDED Requirements

### Requirement: 移动端会话初始化和恢复
Kuikly 聊天体验 SHALL 在选择对话前加载匿名客户端的服务端会话。当列表非空时，若本地记忆的会话仍然存在，则 MUST 选择该会话，否则选择服务端排序后的第一条会话；当列表成功返回空集合时，MUST 创建并选择一个新的空会话。系统 MUST NOT 仅因会话列表或历史加载失败而创建替代会话。

#### Scenario: 创建第一个空会话
- **WHEN** 移动端会话初始化成功列出空的会话集合
- **THEN** ViewModel 创建一个服务端会话、选择该会话、将其 ID 保存为最后选择，并展示空对话

#### Scenario: 恢复仍然有效的上次选择
- **WHEN** 初始化返回多个会话，且本地记忆的会话 ID 仍在列表中
- **THEN** ViewModel 选择该会话并加载消息，且不创建额外会话

#### Scenario: 从过期选择回退
- **WHEN** 初始化返回非空会话，但本地记忆的会话 ID 已不存在
- **THEN** ViewModel 选择服务端排序后的第一条会话，并用该 ID 替换本地记忆值

#### Scenario: 列表加载失败时不创建会话
- **WHEN** 初始会话列表请求失败
- **THEN** UI 展示可重试的初始化错误，并且不调用会话创建接口

#### Scenario: 历史加载失败时保留当前会话
- **WHEN** 已选会话的历史请求失败
- **THEN** UI 保留该会话选择、展示可重试的历史错误，并且不创建替代会话

### Requirement: 持久的多轮对话
Kuikly 聊天体验 SHALL 将每个新的逻辑轮次发送到当前选择的会话，并 MUST 在成功后保持该会话处于选中状态。每个新的逻辑轮次 MUST 获得一个新的非空 `client_message_id`，同一对话内的连续轮次 MUST 使用相同的会话 ID。

#### Scenario: 在同一个会话中完成两轮对话
- **WHEN** 用户在未新建或切换会话的情况下连续成功发送两条消息
- **THEN** 两次仓储调用使用相同的会话 ID 和不同的客户端消息 ID，UI 按顺序展示两组持久化的用户/助手消息

#### Scenario: 发送过程不创建会话
- **WHEN** 用户从已经初始化并选中的会话发送消息
- **THEN** ViewModel 针对该会话调用 `sendMessage`，且发送流程不调用 `createSession`

#### Scenario: 用持久化结果替换乐观消息
- **WHEN** 发送接口返回持久化的用户消息和助手消息
- **THEN** UI 使用服务端结果替换乐观用户项和助手加载项，且不产生重复气泡

### Requirement: 有序历史加载和过期结果保护
Kuikly 聊天体验 SHALL 在会话被选中时加载其消息，保持仓储返回的原始顺序，并且只有异步历史结果仍属于当前选择和当前加载代次时才应用该结果。

#### Scenario: 加载持久化的对话历史
- **WHEN** 用户选择一个包含历史消息的会话
- **THEN** UI 使用稳定的服务端消息 ID，按照仓储返回顺序展示消息

#### Scenario: 忽略上一个会话的延迟响应
- **WHEN** 会话 A 开始加载后用户选择会话 B，且会话 A 的响应在选择变化后才返回
- **THEN** 会话 A 的响应不会替换会话 B 的加载状态或可见消息

#### Scenario: 页面重建后恢复历史
- **WHEN** 同一匿名安装实例重新创建页面，且本地记忆的会话仍然存在
- **THEN** 初始化选择该会话，并展示从服务端读取的持久化消息

### Requirement: 幂等乐观发送和重复操作保护
Kuikly 聊天体验 SHALL 为每个活动发送保存一条待处理轮次记录，其中包含会话 ID、规范化内容、客户端消息 ID 和乐观消息标识。在发送尝试进行期间，系统 MUST 拒绝重复发送操作，并 MUST 禁止会把待处理轮次移动到其他对话的新建、切换和删除会话操作。

#### Scenario: 忽略重复发送点击
- **WHEN** 活动仓储调用完成前，发送操作被连续触发多次
- **THEN** 系统只启动一次仓储发送，并且只展示一组乐观用户消息和助手加载项

#### Scenario: 校验不通过时不改变输入状态
- **WHEN** 输入为空白，或当前没有处于就绪状态的已选会话时触发发送
- **THEN** 系统不添加乐观消息，也不启动仓储发送

#### Scenario: 活动发送期间阻止会话变更
- **WHEN** 仓储发送请求正在进行
- **THEN** 新建、切换和删除会话操作均不会改变当前会话

### Requirement: 重试和不确定结果对账
发送发生错误后，Kuikly 聊天体验 SHALL 保留失败的逻辑轮次及其原始 `client_message_id`。系统 MUST 尝试从服务端历史对账当前会话，并 MUST 在用户明确重试时使用相同的会话 ID、规范化内容和客户端消息 ID。重试 MUST NOT 再追加一条用户气泡。

#### Scenario: 使用相同身份重试失败轮次
- **WHEN** 一次发送失败且用户触发重试
- **THEN** 仓储接收到原始会话 ID、内容和客户端消息 ID，同时复用已有的失败或加载展示项

#### Scenario: 对账客户端报错但服务端已完成的请求
- **WHEN** 发送报告错误，但随后的历史加载包含匹配的用户消息及其后续持久化助手回复
- **THEN** UI 使用持久化消息对替换乐观失败状态，并清除重试状态

#### Scenario: 恢复已持久化但没有助手回复的用户消息
- **WHEN** 加载到的历史最后一条是带有非空客户端消息 ID、且后面没有助手消息的用户消息
- **THEN** UI 只展示一次该用户消息，展示可重试的回复缺失状态，并使用相同的客户端消息 ID 重试

#### Scenario: 对账也失败时保留重试能力
- **WHEN** 发送失败，且随后用于对账的历史请求也失败
- **THEN** 原始逻辑轮次保持可见且可使用原始客户端消息 ID 重试

#### Scenario: 未解决失败后禁止开始新轮次
- **WHEN** 当前会话存在一个可恢复的失败轮次
- **THEN** 在该轮次成功或用户选择其他会话前，UI 不启动新的逻辑轮次

### Requirement: 会话创建、切换和删除
Kuikly 聊天体验 SHALL 提供会话列表入口、当前会话标题、显式新建操作、会话选择和删除确认。当列表刷新成功时，展示的会话集合 MUST 遵循服务端返回的顺序。

#### Scenario: 创建并选择新会话
- **WHEN** 没有活动发送时用户触发新建会话
- **THEN** ViewModel 创建一个会话、选择该会话、持久化其选择，并展示空历史

#### Scenario: 切换会话
- **WHEN** 没有活动发送时用户选择另一个已有会话
- **THEN** ViewModel 持久化该选择、加载目标会话历史，并更新标题栏

#### Scenario: 取消删除会话
- **WHEN** 用户打开删除确认后选择取消
- **THEN** 系统不调用仓储删除，当前选择和历史保持不变

#### Scenario: 删除非当前会话
- **WHEN** 用户确认删除当前会话以外的会话
- **THEN** 仓储删除该会话，当前对话仍然保持选中和可见

#### Scenario: 删除当前会话且仍有其他会话
- **WHEN** 用户确认删除当前会话，且服务端仍有至少一个剩余会话
- **THEN** ViewModel 选择服务端排序后的第一条剩余会话、持久化其 ID，并加载其历史

#### Scenario: 删除最后一个会话
- **WHEN** 用户确认删除当前会话，且服务端已无剩余会话
- **THEN** ViewModel 创建并选择一个新的空会话

### Requirement: 会话和消息状态展示
Kuikly UI SHALL 区分初始化加载、历史加载、空会话、已加载消息、助手生成、可重试发送失败，以及可重试的列表或历史失败。输入和操作控件 MUST 反映当前会话是否能接受新轮次；消息列表 MUST 保持长文本可读，并展示新追加或恢复出的尾部内容。

#### Scenario: 在对话中展示助手生成状态
- **WHEN** 有效发送正在等待仓储结果
- **THEN** 用户消息和助手加载项均可见，发送控件被禁用，列表滚动到可看到待处理轮次的位置

#### Scenario: 展示可重试的助手失败状态
- **WHEN** 对账后发送仍然未解决
- **THEN** 失败的助手区域展示安全的错误信息，以及与该逻辑轮次关联的重试操作

#### Scenario: 区分历史加载和空历史
- **WHEN** 已选会话的消息仍在加载
- **THEN** UI 展示加载状态，而不是空会话提示

#### Scenario: 展示长消息内容
- **WHEN** 历史或发送结果包含 API 长度限制以内的长文本
- **THEN** 消息在列表中保持可读，不被截断成单行预览

### Requirement: 成功发送后的会话元数据刷新
逻辑轮次成功完成后，Kuikly 聊天体验 SHALL 刷新会话列表，以展示服务端生成的标题和按更新时间降序排列的顺序。元数据刷新失败 MUST NOT 将已经完成的消息对改成发送失败。

#### Scenario: 刷新首条消息标题和排序
- **WHEN** 新会话中的第一轮对话成功
- **THEN** ViewModel 请求会话列表、保持同一会话选中，并在刷新成功时应用服务端返回的标题和顺序

#### Scenario: 元数据刷新失败时保留成功消息
- **WHEN** 消息对发送成功，但后续会话列表刷新失败
- **THEN** 消息对仍以成功状态展示，且用户可以继续当前对话
