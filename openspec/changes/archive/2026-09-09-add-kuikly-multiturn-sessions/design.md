## 上下文

服务端和移动端网络层已经提供匿名客户端会话 API：创建、列出、删除会话，读取有序消息历史，以及携带调用方生成的 `client_message_id` 同步发送消息。Go 聊天工作流会根据传入的会话读取已完成消息作为 AI 上下文，对同一会话的生成请求进行串行化，并能在客户端使用相同内容和相同客户端消息 ID 重试时恢复中断的发送操作。

当前移动端 `SessionViewModel` 尚未采用这个会话生命周期。它在每次 `sendMessage()` 内创建新会话，只保存临时 UI 消息，也没有初始化、历史、选择、删除或重试状态。发送失败还可能发生在服务端已经保存用户消息之后，因此如果每次重试都被视为新的逻辑轮次，就会破坏现有幂等契约。

UI 使用 Kuikly Compose 实现。框架已经提供生命周期绑定的 `ViewModel` 作用域、Compose 响应式状态、`LazyColumn`、对话框和 `ModalNavigationDrawer`，所以会话体验可以全部保留在共享代码中。

## 目标 / 非目标

**目标：**

- 在一个已选服务端会话中持续发送多轮消息，使服务端能把之前的消息作为 AI 上下文。
- 页面或应用重新创建后恢复会话和有序消息历史。
- 提供明确的新建、切换和删除会话操作。
- 分离初始化、历史、发送和错误状态，让每种失败拥有正确的恢复操作。
- 在一个逻辑轮次的整个生命周期内保留同一个 `client_message_id`，并将乐观 UI 与服务端持久化状态对账。
- 防止过期异步结果和重复用户操作破坏当前会话状态。
- 保持远程仓储与模拟仓储可替换，并用确定性的 common tests 覆盖编排行为。

**非目标：**

- 流式 token、取消生成或展示部分助手内容。
- 在同一个页面实例中并发生成多个会话。
- 消息编辑、分支、重新生成、手工修改标题、搜索或历史分页。
- 修改 Go REST API、Python gRPC API、MySQL 表结构、Redis Key 或认证模型。
- 完整 Android/iOS 交互验收；这仍属于阶段 11。

## 决策

### 1. 将已选服务端会话作为对话边界

`SessionViewModel` 负责持有 `sessions`、`currentSessionId` 和当前会话消息。初始化时先列出会话：如果本地记录的会话仍然存在，则恢复该选择；否则选择服务端排序后的第一条；只有会话列表成功返回空集合时才创建并选择一个新会话。用户点击“新建会话”时则显式创建并选择空会话。

每次发送都使用 `currentSessionId`，发送流程本身绝不创建新会话。这样后续发送才是真正的后续轮次，而不是互相隔离的单次补全。

曾考虑在第一次发送时延迟创建会话。虽然可以避免空会话记录，但它与阶段 10“首次打开进入空会话”的验收目标冲突，也会增加标题、选择和失败重试状态的复杂度，因此采用在权威列表为空后立即创建的方案。

### 2. 本地只持久化最后所选会话 ID

新增一个小型 `SelectedSessionStore` 抽象，通过当前 Pager 的 `SharedPreferencesModule` 读写和清除最后所选会话 ID。会话和消息仍以服务端为唯一事实来源。本地 ID 只有在最新 `listSessions()` 结果中仍然存在时才有效；过期 ID 会被当前回退选择替换。

曾考虑在本地持久化完整会话和消息，但这会引入缓存失效和匿名身份重置问题，而 MVP 并不需要离线历史。

### 3. 使用独立操作状态替代单一加载标记

ViewModel 分别暴露初始化、历史加载、会话变更和发送状态。初始列表或创建失败占据页面并提供初始化重试；历史失败保留当前选择并提供历史重试；发送失败则附着于对应的逻辑轮次。发送进行期间拒绝会话管理操作和新的发送操作。

这样可以避免单个 `isLoading` 将标题刷新失败错误地表现为模型回复失败，或把空状态和加载状态混为一谈。

### 4. 为瞬时状态和持久状态引入展示层消息模型

仓储层 `ChatMessage` 继续表示服务端持久化记录。UI 使用单独的展示模型，包含稳定 UI Key、可选服务端消息 ID、角色、内容、展示/投递状态，以及用户轮次对应的 `client_message_id`。

发送时，ViewModel 先追加一条乐观用户消息和一条助手加载占位。成功后使用服务端返回的持久化消息对替换这两项，而不是再次追加。加载历史时使用服务端消息 ID 映射成稳定的 UI 项。

曾考虑只给当前 `Message` 增加一个错误字段，但这不足以表达重试身份，也无法对账服务端状态不确定的请求。

### 5. 将 `client_message_id` 视为逻辑轮次身份

一个可注入的生成器只在用户开始新的逻辑轮次时创建新的 UUID 形式客户端消息 ID。待处理轮次记录会保存已选会话 ID、规范化后的内容、客户端消息 ID 和乐观消息项 ID。重试复用所有逻辑请求输入；仓储仍为每次 HTTP 尝试生成新的 `X-Request-ID`。

发送发生任何错误后，ViewModel 会尽可能重新加载当前会话历史，再决定最终展示的失败状态。如果服务端实际已完成消息对，历史将替换乐观状态，并将本次发送视为成功；如果历史只有末尾用户消息且 `client_message_id` 相同，则只展示一次该消息，并进入“回复缺失但可重试”状态；如果对账本身也失败，则保留原始待处理轮次，并继续允许使用同一个 ID 重试。

存在未解决的可恢复轮次时，当前会话不能发送新的逻辑消息。用户可以重试；仅在 HTTP 发送尝试实际进行期间禁止切换、新建和删除会话。

### 6. 防止过期历史请求覆盖新的会话选择

每个历史请求都捕获目标会话 ID 和一个单调递增的加载代次。只有当二者仍与当前选择和当前代次一致时，请求结果才允许更新可见消息。切换会话会先递增加载代次，再启动新的历史请求。即使某个平台传输层无法及时取消旧 HTTP 调用，该方案仍然有效。

### 7. 保持服务端会话排序，并在变更后刷新

服务端按 `updated_at` 降序返回的列表是权威顺序。消息成功后，ViewModel 保持当前消息为成功状态，并刷新会话列表，以获取服务端生成的首条消息标题和最新排序。刷新失败不会把已完成轮次改成失败，只会使列表元数据暂时保持旧值，等待下次刷新。

删除非当前会话后，不改变当前对话。删除当前会话后，选择服务端排序中剩余的第一条并加载历史；如果没有剩余会话，则创建并选择新的空会话。只有选择确认有效后才更新本地记忆的会话 ID。

### 8. 使用模态导航抽屉管理会话

`SessionScreen` 使用 Kuikly Compose `ModalNavigationDrawer` 包裹聊天界面。抽屉中包含新建会话操作和服务端会话懒加载列表；标题栏负责打开抽屉并显示当前会话标题；删除操作使用确认对话框，避免误删。

消息区域分别表达初始化加载、历史加载、历史失败、空历史、正常消息、助手生成中和可重试回复失败。保留现有键盘避让逻辑以及使用稳定 Key 的 `LazyColumn`。当前会话变化，或尾部消息的身份/状态变化时触发自动滚动。

### 9. 只从历史中恢复明确无歧义的末尾用户轮次

当前 REST 历史响应不包含发送操作状态，因此客户端只在最后一条持久化消息为用户角色且具有非空 `client_message_id` 时，推断它是可恢复的中断轮次。客户端不会把更早的不匹配用户消息推断为待重试状态，也不会为缺少 ID 的历史消息虚构 ID。

这是偏向安全的选择，避免修复含义不明确的历史结构。如果未来需要更丰富的恢复能力，可以新增发送操作状态端点来替代该推断。

## 风险 / 权衡

- **用户看到传输错误时，服务端可能已经完成请求** → 在确定错误 UI 前重新加载历史，并在重试时复用原始客户端消息 ID。
- **旧历史请求可能覆盖刚切换的新会话** → 每个历史结果同时校验会话 ID 和加载代次。
- **REST API 没有暴露发送操作状态** → 只恢复带客户端消息 ID 的末尾用户消息；含义不明确的历史保持只读。
- **成功回复后的会话标题或列表刷新可能失败** → 保留成功消息，把元数据刷新失败视为非致命错误。
- **发送期间禁用所有会话管理操作略显严格** → MVP 接受该限制以避免跨会话待处理状态；需要并发多会话任务时再扩展。
- **历史接口没有分页** → MVP 先接受中小规模会话；支持超长历史前增加基于消息序号的分页。
- **用户反复新建会话可能累积空会话** → MVP 允许显式空会话，并提供删除功能；自动清理不在本次范围内。

## 迁移计划

1. 在不改变仓储契约的前提下，增加展示状态、本地会话选择存储和可注入客户端消息 ID 生成器。
2. 在 `SessionViewModel` 中用初始化、选择、历史、发送、对账、重试和删除编排替代旧的“每次发送创建会话”流程。
3. 在共享 Kuikly UI 中增加会话抽屉、动态标题、分类状态内容、重试控件和禁用状态。
4. 增加确定性 common tests，然后运行共享代码测试及当前环境可执行的移动端构建检查。
5. 只有全部验收场景通过后，才更新路线图中的阶段 10 完成状态。

回退只需还原移动端共享代码变更，不需要服务端或存储数据迁移。新 UI 创建的会话在现有 API 下仍然有效。
