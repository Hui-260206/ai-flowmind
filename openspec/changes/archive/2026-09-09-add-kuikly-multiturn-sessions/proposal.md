## 背景

移动端聊天页目前每次发送消息都会创建一个新的服务端会话，因此即使 Go API 已具备会话、历史记录和上下文能力，用户仍无法连续多轮对话、恢复历史或管理已有会话。阶段 10 需要把这个临时的单消息流程升级为可恢复的持久会话体验，同时保持服务端既有的幂等和故障恢复保证。

## 变更内容

- 在连续发送过程中维护同一个已选服务端会话，使后续轮次使用同一份对话上下文。
- 页面进入时加载匿名客户端的会话列表，优先恢复仍然有效的上次选择；只有不存在任何会话或用户明确新建时才创建空会话。
- 打开或切换会话时加载并展示服务端持久化的消息历史。
- 在 Kuikly UI 中增加会话列表入口、当前标题、新建、切换和删除会话交互。
- 将初始化、历史加载、发送和可恢复错误建模为相互独立的 UI 状态。
- 每个逻辑用户轮次生成一个稳定的 `client_message_id`，重试时继续使用该 ID，并在发送期间阻止重复请求。
- 在发送成功或结果不确定时，将乐观消息与服务端持久化消息对账，包括恢复“用户消息已保存、助手回复尚未完成”的状态。
- 第一轮成功后刷新会话排序和服务端生成的标题。
- 增加 ViewModel 与 UI 层测试，覆盖多轮连续性、会话恢复、切换、删除、防重复点击、过期异步结果保护和重试行为。

## 能力

### 新增能力

- `kuikly-session-experience`：定义移动端会话生命周期、多轮消息状态、历史恢复、会话管理 UI 和幂等重试行为。

### 修改的能力

- 无。现有 `kuikly-chat-network` 仓储和 REST 契约已经提供本次变更所需的操作。

## 影响

- 影响 Kuikly 共享移动端页面、`SessionViewModel`、聊天 UI 模型、消息列表、输入栏、标题栏及新增的会话列表组件。
- 复用现有 `ChatRepository`，不修改公开 Go REST API、Python gRPC API、MySQL 表结构或 Redis 协议。
- 可能新增一个用于保存最后所选会话 ID 的轻量本地偏好抽象，以及便于确定性测试的消息 ID 生成器注入点。
- 扩充移动端状态转换和仓储编排相关的 common tests。
- 实现及验收完成后更新 `docs/roadmap/MVP_EXECUTION_PLAN.md` 的阶段 10 状态。
